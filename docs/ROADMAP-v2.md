# Minux v2.0 开发路线图

v2.0 建议继续以单核 RISC-V 64、QEMU `virt` 为正式发布平台。这个版本要让用户能在自己的 shell 里切换目录、按名称运行命令、组合多级管道，并用 Ctrl-C 中断整条前台管道。每个操作都对应一项内核能力、一个 libc 接口和一组可重复的测试。

v1.0 已有抢占式调度、COW fork、ELF 加载、按需分配匿名页、管道和串口 TTY。`/tmp` 可写，`/disk` 是只读 ext2。现有 shell 要求绝对命令路径，只能连接两个命令。下表从这个基线出发，版本号表示建议的开发顺序。[v1.0 路线图](ROADMAP.md) · [内存管理](MM.md) · [文件系统](FS.md)

## 里程碑

| 版本 | 里程碑 | 要做的事 | 完成标准 | 状态 |
|---|---|---|---|---|
| v1.1 | 收拢架构相关代码 | 让构建按架构选择工具链、链接脚本、用户启动代码和测试。把 `init/main.c` 中的 SBI、设备树探测及中断控制器初始化移回 RISC-V 平台层。通用启动代码接收可用内存、保留区和启动设备。 | 默认 `make run` 进入原有 shell；`make test` 两张盘各通过 v1.0 的 537 项检查和串口场景，磁盘子程序仍分别返回 42、73。 | 已完成（2026-11-27） |
| v1.2 | 用户地址空间与堆 | 在已有 VMA、缺页和 COW 路径上实现私有匿名 `mmap`、`munmap`，支持部分解除映射以及 VMA 拆分。libc 增加 `malloc/free/realloc`，shell 用堆保存命令行和参数。 | 用户程序跨页写入，fork 后父子写互不影响；解除中间一页后两侧仍可读写，单独的子进程访问已解除页会终止。反复分配、扩容和退出后，测试核对页面回收；shell 能处理超过原 127 字节上限的命令行。 | 已完成（2026-11-28） |

v1.1 已从干净构建目录通过验收。默认 `make run` 进入 `minux$` 并成功读回管道重定向的文件。双盘各通过原有 22 组、537 项内核检查，其中 Sv39 为 43 项。磁盘子程序退出码分别为 42、73，串口行编辑、Ctrl-D、管道和错误恢复均通过。[构建与测试](../README.md#测试) · [v1.0 基线](BASELINE-v1.0.md)

v1.2 已从干净构建目录通过验收。双盘各通过 22 组、588 项内核检查（其中 Sv39 为 58 项、mm 为 57 项、user wait 为 47 项），`/test/mmap` 与 `/test/commands` 覆盖 `errno` 转换、跨页匿名映射与 COW、中间页解除与子进程 `SIGSEGV`、堆反复分配扩容及页面回收，脚本与串口交互均验证超过原 127 字节上限的长命令行。

v1.5 的串口验收用例（在 Minux shell 中逐行输入）：

```sh
cd /tmp
echo "hello Minux" | cat | wc -l > count
cat < count
```

## 内核怎样向 Linux 靠近

- **进程与调度。** v1.4 把运行队列和任务切换、父子关系和退出回收、信号投递分别组织。TTY 记录前台进程组，调度器负责让可中断睡眠的任务重新就绪，退出路径负责让父进程读到信号退出状态。覆盖三条容易出错的路径：CPU 上运行的任务、睡在 TTY 上的任务、睡在管道上的任务。继续使用单核调度即可验证这些语义。[现有调度与等待设计](SCHED.md)
- **路径与打开文件。** v1.3 把挂载位置和目录项放进路径对象，由任务持有 cwd；目录查找和枚举由文件系统实现，打开位置与读写操作属于打开的文件。ramfs 和 ext2 走同一条路径解析流程。重点检查跨挂载点的 `..`、fork 继承 cwd 和 fd 共享偏移。按这些操作需要引入 Linux 的 VFS 抽象。[Minux VFS](FS.md) · [Linux VFS 对照](https://docs.kernel.org/filesystems/vfs.html)
- **用户 ABI。** 内核保留现有 RV64 系统调用编号及负错误码约定。v1.2 集中处理 libc 错误转换：先保留内核原始返回值的内部入口，再让公开的系统调用包装按接口返回 `-1` 或 `MAP_FAILED` 并设置 `errno`。同阶段迁移并测试依赖旧 libc 负错误码的调用者。新接口逐项记录支持的参数、标志和失败语义。[现有 libc 接口](../user/libc/include/unistd.h)

## x86-64 什么时候做

建议分两步。**v2.0 内完成可移植性准备，并安排一次 x86-64 单核启动试验；v2.0 之后再把 x86-64 做成正式支持的平台。** v1.1 已将工具链、QEMU 机型和架构测试纳入 RISC-V 构建配置，设备树解析与设备初始化也已移入平台层。x86-64 原型可以复用通用启动入口与启动内存表。若同时要求 x86 跑通正式 shell，还得一起完成页表、异常入口、上下文切换、用户 ABI 和磁盘驱动适配，会占用本轮内核与用户环境的开发时间。[构建入口](../Makefile) · [通用启动入口](../init/main.c)

| 时机 | 范围 | 验收与决定 |
|---|---|---|
| v1.1 完成后 | 在 `arch/x86/` 做 x86-64 原型：固定一套 QEMU PC 机型和引导协议，接入启动栈、内存图和早期串口。 | 独立构建目录生成可引导镜像，在单 vCPU 下从通用启动路径打印可用内存。记录启动命令及仍依赖 RISC-V 的位置；试验若需先完成用户态或磁盘支持，就记录阻塞点，继续 v1.2。原型单列验收，v2.0 发布按上表判定。 |
| v2.0 发布后 | 依次移植分页与异常、定时器与任务切换、x86-64 系统调用入口和 libc 启动代码；把汇编版 `/init` 与磁盘测试程序中的通用逻辑移到 C，接入适合该机型的块设备。 | 先在用户态运行一个静态 C 程序，再启动同源 shell；两种架构分别运行通用内核、libc、磁盘和串口回归后，将 x86-64 列为正式支持。 |

## 后续候选

优先考虑只读 procfs 和 `ps`，用 v1.3 的目录接口和 v1.4 的进程组信息展示任务状态。持久化写入可单独规划块设备写请求、缓存一致性、ext2 元数据更新和重启校验。SMP、网络、页面回收与 swap、sysfs、动态链接和可加载模块分别留给后续版本评估。
